# Contributing to ChurnCast

This repository is a **learning project** from [AiCanCode](https://www.aicancode.org). Students work in their own
fork; maintainers improve the starter, the docs and the reference solution here.

## Workflow (students and maintainers alike)
1. **One issue per change.** Use the *Modelling question* or *Bug or wrong number* template.
2. **Branch from `main`:** `git switch -c feat/m3-point-in-time-features` (`feat/`, `fix/`, `test/`, `docs/`, `chore/`).
3. **Small commits, [Conventional Commits](https://www.conventionalcommits.org/) messages:**
   `feat(sql): tickets known at the cut-off`, `test(r): a resolution after S is still open`, `docs: phase 3 M4`.
4. **Run the checks locally before pushing**, exactly what CI runs:
   ```bash
   cd tracks/<python|sql|r>
   make lint test            # seconds, tiny fixture
   make coverage run gate report   # data and model tests on the real export, the gate, the report
   ```
   A change that moves any number also needs `python3 scripts/parity.py` against the golden files.
5. **Open a pull request** and fill in the template, including *Numbers check* and *AI assistance*.
6. **CI must be green** and the PR self-reviewed against the checklist before merge (squash merge).

## Code style
| Track | Formatter / linter | Command |
|---|---|---|
| Python | Ruff (lint + format) | `make lint` · auto-fix: `.venv/bin/ruff format .` |
| SQL | sqlfluff (DuckDB dialect) + Ruff for the runner | `make lint` · auto-fix: `.venv/bin/sqlfluff fix sql/*.sql` |
| R | lintr (tidyverse style, `.lintr`, native pipe `\|>`) | `make lint` (in the dev image) · auto-format: `styler::style_pkg()` |

## Keep the three tracks in sync (maintainers)
* `contract/feature-spec.md` defines every cleaning rule, feature, metric and gate check; `data-contract.yaml` the
  numbers; `metrics.schema.json` and `model.schema.json` the outputs. A behaviour change = contract change (with a
  version bump) + all three tracks + the tiny fixture's expected values + the golden files.
* The golden files are regenerated only on purpose, and only when all three tracks agree
  (`python3 scripts/parity.py <golden> tracks/*/out/metrics.json` → MATCH). A golden file is never edited by hand.
* The raw exports are generated by `scripts/generate_data.py` (seeded); `--check` proves the committed files are
  byte-identical to it.
* The `solution` branch has one annotated tag per phase. If you change an early phase, rebase the later phase
  commits and **move the tags**, then run `scripts/verify-tags.sh`. Every tag must pass.

## Data, models and privacy
The exports are synthetic, but treat them like real customer data: no row-level data in issues, logs, prompts or
screenshots; aggregates only. `cancellation_reason` is never a feature, `age_band` is used only to check fairness,
and the AI explainer never sees either.

## Using AI assistants
Allowed and encouraged, with the rules in [`AI_LOG.md`](AI_LOG.md): no secrets or rows in prompts, verify every
output, log what you kept and rejected.
